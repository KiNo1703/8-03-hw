# Задание 1. Резервное копирование

## 1.1. Восстановление данных в полном объёме за предыдущий день

1. Полное резервное копирование (Full Backup)

Что это: Ежедневное создание полной копии всей базы данных.

Почему подходит:
Простота восстановления: Для восстановления требуется только один резервный набор. Это быстро и минимизирует риск ошибок.
Предсказуемость: Соответствует требованию "данные на конец предыдущего дня".
Надёжность: Все данные находятся в одном месте и в непротиворечивом состоянии (если бэкап транзакционно согласован).

Недостатки:
Большой объём хранимых данных.
Длительное время создания бэкапа и высокая нагрузка на систему.


2. Комбинированная стратегия: Полное + Инкрементное/Дифференциальное копирование

Что это:
Полный бэкап делается, например, в воскресенье вечером.
Инкрементный бэкап (копируются только данные, изменённые с момента последнего любого бэкапа) делается ежедневно с понедельника по субботу.
Дифференциальный бэкап (копируются только данные, изменённые с момента последнего полного бэкапа) делается ежедневно.

Для восстановления состояния на "вчера" потребуется:
При инкрементной стратегии: Последний полный бэкап + все инкрементные бэкапы до вчерашнего дня (включительно).
При дифференциальной стратегии: Последний полный бэкап + вчерашний дифференциальный бэкап.

Недостатки:
Процесс восстановления сложнее, чем при использовании только полных бэкапов.
Требует более тщательного управления цепочкой бэкапов.

## 1.2. Восстановление данных за час до предполагаемой поломки

Подходящие варианты резервного копирования:

1. Резервное копирование журналов транзакций (Transaction Log Backup) в комбинации с полным копированием

Что это: Полное копирование выполняется регулярно (например, раз в неделю), а журнал транзакций архивируется каждые 15-60 минут.

Почему подходит:
Это единственный способ гарантировать точное восстановление на момент времени.
Позволяет выполнить восстановление на момент времени (Point-in-Time Recovery - PITR). Вы восстанавливаете полный бэкап, затем последовательно накатываете все журналы транзакций вплоть до конкретной минуты за час до поломки.
Обеспечивает минимальную потерю данных.

Как это работает:
Восстановить последнюю полную резервную копию базы данных с состоянием NORECOVERY.
Восстановить все последние дифференциальные копии (если они используются) с состоянием NORECOVERY.
Восстанавливать журналы транзакций последовательно, один за другим, и остановиться на том журнале, который покрывает время "за час до поломки".


2. Непрерывное резервное копирование и репликация данных (Continuous Backup & Replication)

Что это: Технологии, которые постоянно фиксируют изменения данных почти в реальном времени, часто с использованием репликации на отдельный сервер.
Снимки состояния (Snapshots): Частое (каждые несколько минут/час) создание снимков файловой системы или СХД.
Репликация на уровне БД: Транзакционная репликация, потоковая репликация в PostgreSQL.
Технологии CDP (Continuous Data Protection): Фиксируют каждое изменение, позволяя "отмотать" данные на любой момент в прошлом.

Почему подходит:
Обеспечивает очень низкий RPO (возможно, несколько минут или даже секунд).
Позволяет быстро поднять реплику базы данных, которая будет отставать от основной на заданный интервал (например, на 1 час), что идеально соответствует условию "за час до поломки".

# Задание 2. PostgreSQL

## 2.1. Резервное копирование с помощью pg_dump
pg_dump создаёт дамп базы данных — файл с SQL-командами, которые можно выполнить для восстановления БД в том же состоянии.

Синтаксис:


`pg_dump [ОПЦИИ] [ИМЯ_БАЗЫ_ДАННЫХ]`

Практические примеры:

Создание простого дампа в формате SQL:
Создаёт текстовый файл с SQL-командами.


`pg_dump mydatabase > mydatabase_backup.sql`

Создание дампа в пользовательском (custom) формате:
Это гибкий формат, поддерживающий сжатие, параллельное восстановление и выборочное восстановление. Это рекомендуемый вариант для большинства случаев.


`pg_dump -Fc mydatabase > mydatabase_backup.dump`

-Fc — формат вывода custom.

Создание сжатого дампа в пользовательском формате с указанием хоста и пользователя:


`pg_dump -h localhost -U myuser -Fc mydatabase > mydatabase_backup.dump`

Создание дампа всей кластера баз данных (всех БД) с помощью pg_dumpall:
Это полезно для резервного копирования глобальных объектов (ролей, прав), но для больших БД лучше делать дампы по отдельности.


`pg_dumpall > cluster_backup.sql`

## 2.2. Восстановление с помощью pg_restore

pg_restore используется для восстановления из дампов, созданных в архивных форматах (например, custom -Fc или directory -Fd). Для простых SQL-файлов используется psql.

Синтаксис:


`pg_restore [ОПЦИИ] [ФАЙЛ_С_ДАМПОМ]`
Практические примеры:

Восстановление базы данных в новую (пустую) БД:
Это самый частый сценарий.

 Сначала создаем пустую базу данных (например, через psql)
`createdb -h localhost -U myuser new_database`

 Затем восстанавливаем в нее из дампа
`pg_restore -h localhost -U myuser -d new_database mydatabase_backup.dump`

-d new_database — указывает, в какую базу данных производить восстановление.

Восстановление с параллельными jobs для ускорения:


`pg_restore -h localhost -U myuser -d new_database -j 4 mydatabase_backup.dump`

-j 4 — использует 4 параллельных процесса для восстановления.

Восстановление только структуры данных (без данных):

`pg_restore -h localhost -U myuser -d newdatabase --schema-only mydatabase_backup.dump`

Восстановление только данных (в уже существующую структуру):

`pg_restore -h localhost -U myuser -d newdatabase --data-only mydatabase_backup.dump`

Просмотр содержимого дампа (что в нем находится):

`pg_restore --list mydatabase_backup.dump`

## Итог
Для гибкости и производительности: Используем pg_dump -Fc и pg_restore.
Для простоты и прозрачности: Используем pg_dump без опций (создаст .sql файл) и psql для восстановления.
Для резервного копирования всех БД и ролей: Используем pg_dumpall.


# Задание 3. MySQL

В MySQL инкрементное резервное копирование реализуется не одной универсальной командой, а связкой действий и основано на использовании бинарных логов (binary logs).
Бинарные логи содержат все операции изменения данных (DML и DDL), произошедшие в базе данных с момента их включения. Восстановление до точки сбоя — это процесс применения этих изменений к полной резервной копии.

## 3.1. Процесс инкрементного резервного копирования в MySQL

Шаг 0: Предварительная настройка
Убедитесь, что бинарные логи включены. Для этого в конфигурационном файле my.cnf / my.ini должны быть строки:

`[mysqld]
server-id = 1
log-bin = mysql-bin  # Включает бинарное логирование и задаёт базовое имя для файлов логов
binlog_format = ROW  # Рекомендуемый формат для надежности и совместимости`

После изменения конфигурации перезапустите сервер MySQL.

Шаг 1 Создание Полной Резервной Копии (Full Backup)
Это отправная точка для всех будущих инкрементных бэкапов.


`# Блокируем таблицы на запись и фиксируем текущую позицию в бинарном логе
mysqldump -u root -p \
  --single-transaction \
  --flush-logs \
  --master-data=2 \
  --all-databases > full_backup_$(date +%Y%m%d).sql`
  
Пояснение ключевых опций:

--single-transaction: Создает согласованный на момент начала дампа снимок данных, не блокируя таблицы для чтения (для InnoDB).

--flush-logs: Закрывает текущий бинарный лог и начинает новый. Это критически важно, так как оно "отсекает" изменения, разделяя полный бэкап и последующие инкрементальные.

--master-data=2: Записывает в дамп имя файла и позицию текущего бинарного лога. Эта информация жизненно необходима для последующего применения инкрементных копий.


Шаг 2: Создание Инкрементной Резервной Копии (Incremental Backup)
Инкрементный бэкап в этом контексте — это просто копирование бинарных логов, созданных с момента последнего полного или инкрементного бэкапа.

Сначала принудительно переключим бинарный лог, чтобы получить четкую границу:

`mysql -u root -p -e "FLUSH BINARY LOGS;"`

Теперь скопируем все бинарные логи, кроме самого последнего (текущего).

Предположим, после полного бэкапа у нас появились логи mysql-bin.000002 и mysql-bin.000003, а после FLUSH начался mysql-bin.000004.


 Копируем логи, которые нужно сохранить (с 000002 по 000003)
 
`cp /var/lib/mysql/mysql-bin.00000[2-3] /path/to/backup/folder/`

Также обязательно копируем индексный файл

`cp /var/lib/mysql/mysql-bin.index /path/to/backup/folder/`

## Процесс Восстановления из Инкрементного Бэкапа

Восстановление — это двухэтапный процесс.
Восстановление полной резервной копии:

`mysql -u root -p < full_backup_20241028.sql`

Применение инкрементных изменений из бинарных логов.

Нужно применить все логи, созданные после момента создания полного бэкапа. Позицию можно посмотреть в дампе (строка CHANGE MASTER TO..., которую добавила опция --master-data=2).


`Применяем все инкрементные логи, начиная с указанной в дампе позиции
mysqlbinlog /path/to/backup/folder/mysql-bin.000002 /path/to/backup/folder/mysql-bin.000003 | mysql -u root -p
Для восстановления на момент времени (Point-in-Time Recovery - PITR):`


`Восстанавливаем данные до 13:30 дня поломки
mysqlbinlog --stop-datetime="2024-10-28 13:30:00" /path/to/backup/folder/mysql-bin.000002 /path/to/backup/folder/mysql-bin.000003 | mysql -u root -p`

## Итог

В  MySQL инкрементное резервное копирование - это стратегия, а не одна команда. Ключевые этапы:
1) Включить log-bin.
2) Создать полный бэкап с --flush-logs и --master-data.
3) Периодически сохранять (копировать) закрытые бинарные логи - это и есть ваш инкрементный бэкап.
4) Для восстановления: Восстановить полный бэкап и применить сохраненные бинарные логи с помощью mysqlbinlog.
